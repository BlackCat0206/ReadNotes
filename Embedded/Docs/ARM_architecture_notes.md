# ARM 体系结构学习笔记（X105 实战版）

> 本文以 X105（SigmaStar SSC308，Cortex-A 双核，32 位 ARM，Linux 5.10.117）为背景，
> 所有案例均来自实际 dmp 崩溃分析（85c46ca3：SIGBUS @ 0xbc88c4）。
> 阅读前提：懂一点 C/C++，会看寄存器和反汇编输出。

---

## 0. 为什么嵌入式开发要懂 ARM

你已经在"用"这些知识了，只是没串起来：

| 现象 | 背后的 ARM 知识 |
|---|---|
| dmp 里 `cpsr = 0x600f0030` | CPSR 标志位与工作模式 |
| `vst1.8 {d16-d17}, [r0 :64]` 崩溃 | NEON 指令 + 对齐规则 |
| SIGBUS 而不是 SIGSEGV | 对齐异常 vs 未映射地址（MMU 页表） |
| 栈回溯 `Found by: call frame info` | 函数调用约定（AAPCS）+ 栈帧 |
| 崩溃 pc 指向故障指令的**下一条** | 异常返回地址规则 |

## 1. ARM 与 x86 的本质区别：Load/Store 架构（RISC）

```
x86:    加法可以直接在内存上做    add [rax], rbx        （CISC：内存即操作数）
ARM:    运算只能在寄存器里做      ldr r2, [r0]    ; 内存→寄存器
                                add r2, r2, r1   ; 运算
                                str r2, [r0]     ; 寄存器→内存   （RISC）
```

- ARM 只有 `ldr`/`str` 两条路访问内存（+ 向量版 `vld1`/`vst1`）；
- 指令宽度固定（ARM 4 字节 / Thumb-2 2~4 字节）→ 流水线好做、功耗低、解码简单 → 嵌入式选 ARM 的原因。

**实战意义**：分析 crash 看到 `ldr/str`，立刻知道"这里在访问 `r0` 指向的内存"，`r0` 就是要盯的指针。

## 2. 寄存器组与 CPSR

### 2.1 两套寄存器，别混淆

| 寄存器 | 名称 | 宽度 | 用途 |
|---|---|---|---|
| `r0`~`r15` | 通用寄存器 | **32 位 = 4 字节** | 普通运算；r13=sp, r14=lr, r15=pc |
| `d0`~`d31` | 双字寄存器（Doubleword） | **64 位 = 8 字节** | 浮点 / NEON 向量 |
| `q0`~`q15` | 四字寄存器（Quadword） | **128 位 = 16 字节** | = 两个 d 寄存器拼起来（q8 = d16+d17） |

### 2.2 通用寄存器分工（AAPCS 调用约定）

```
r0 - r3     函数参数/临时值（调用者保存，传参≤4个，r0 兼返回值）
r4 - r11    局部变量（被调用者保存）
r12         IP（过程调用临时寄存器，编译器自由用）
r13 = sp    栈指针
r14 = lr    返回地址（bl 指令自动写入；pop {.., pc} 时弹回）
r15 = pc    程序计数器
cpsr        程序状态寄存器（标志位 + 模式）
```

### 2.3 实例：dmp 中崩溃线程 thread[77]（thread_id=0x4e5）

```text
r0   = 0xbc88c4     ← 故障地址（vst1.8 的目标）
r4   = 0xbc88c4     ← 被保存在 r4 的 this 指针
sp   = 0x8dd40638   ← 栈指针（栈段 0x8dd40000~0x8dd43000 内 ✓）
lr   = 0x601bb      ← 返回地址
pc   = 0x5f99c      ← 下一条要执行的指令（真正故障指令在 0x5f998！）
cpsr = 0x600f0030   ← 见下
```

### 2.4 CPSR 逐位拆解（0x600f0030）

```
0x600f0030 = 0110 0000 0000 1111 0000 0000 0011 0000
              │││ │                        │││││││
              N││ │                        ││││││└── 模式位 M[4:0] = 0b10000 = User
              Z│ │                        │││││└───── T=1 → Thumb 模式（不是 ARM 模式！）
               C│                        ││││└─────── F=0 未屏蔽 FIQ
                │                        │││└───────── I=0 未屏蔽 IRQ
                └ N=0 Z=1 C=1 V=0         │└─────────── A=0 未禁用异步异常
                                          └──────────── bit24-20 保留/GE
```

- **T 位**：决定反汇编按 Thumb-2 解码（`vst1.8` 是 4 字节 Thumb-2 指令）；
- **模式位**：User(0b10000) / FIQ / IRQ / SVC / ABT / UND / SYS 等。

### 2.5 影子寄存器（banked registers）

每种异常模式（FIQ/IRQ/SVC/ABT/UND）**各有自己的 sp 和 lr**（以及 FIQ 的 r8-r12）。
中断来了硬件自动切到 `sp_irq`，用户态 sp 不丢——内核分析里看到的中断栈就是这个。
FIQ 有独立 r8-r12 → 无需保存即可快速中断，这是 FIQ 比 IRQ 快的原因。

## 3. 异常机制：从指令到 SIGBUS 的完整链路

用户态一条指令出错 → 收到信号，中间 5 层：

```
① 用户态执行 vst1.8 {d16-d17}, [r0]   (r0=0xbc88c4)
        │ 地址只 4 字节对齐，但 :64 要求 8 字节
        ▼
② 产生 Data Abort 异常（同步异常，来自指令本身）
        │ 硬件自动：cpsr→spsr, 当前pc→lr_abt, 切 ABT 模式, 跳异常向量表
        ▼
③ 内核异常向量 → do_DataAbort → 查 MMU 页表：映射合法吗？
        │ 合法（在 duer_lark 的 bss 段）→ 只是对齐问题
        ▼
④ 内核无法在用户态下修复 → 向进程发送 SIGBUS
        ▼
⑤ 用户态 signal handler（crab 的 ExceptionHandler）接管 → 存现场 → 写 dmp
```

### 3.1 异常向量表（ARMv7，启动时由内核填写）

| 地址 | 异常 | 说明 |
|---|---|---|
| 0x00 | Reset | 复位 |
| 0x04 | Undefined | 未定义指令 |
| 0x08 | SWI | 系统调用（svc 指令） |
| 0x0c | Prefetch Abort | 取指失败 |
| 0x10 | Data Abort | **访存失败（我们案例）** |
| 0x18 | IRQ | 外部中断 |
| 0x1c | FIQ | 快速中断 |

### 3.2 中断 vs 异常

| | 异步性 | 来源 | 案例 |
|---|---|---|---|
| 中断（IRQ/FIQ） | 异步 | 外部设备随时插入 | 定时器、网卡、VENC 完成 |
| 异常（Abort/SVC） | 同步 | 指令自己造成 | 缺页、对齐、系统调用 |

### 3.3 返回地址规则（重要！）

异常保存的 lr 与异常类型相关。Data Abort 的 lr = **故障指令的下一条地址**，
所以反汇编必须从 pc **往前翻**（0x5f99c 是 pc，真正出错的 vst1.8 在 0x5f998）。

## 4. vst1.8 深度拆解（本案例题眼）

### 4.1 指令逐段含义

```asm
vst1.8  {d16-d17}, [r0 :64]
   │        │         │  └─ [r0]：目标内存地址（r0 = 0xbc88c4）；:64 见 4.3
   │        │         └──── 存储内容：d16+d17 两个 64 位寄存器 = 128 位 = 16 字节
   │        └────────────── vst1 = Vector STore 1 个寄存器组；.8 = 按 8bit(1字节)元素看待
   └─────────────────────── 翻译：把 d16-d17 的 16 字节写到 [r0] 开始的 16 字节上
```

> `.8` 不是"存 8 次"，只是"按字节看待"。总量由 `{d16-d17}` 决定 = 16 字节。
> 配合 `vmov.i32 q8, #0` 就是 `memset(0xbc88c4, 0, 16)`。

### 4.2 为什么一个寄存器 64 位、两条指令却可"64 位编码"？

- `q8`（128 位）= `d16`（高 64 位）+ `d17`（低 64 位）——ARM 硬性拼装规定；
- 所以 `{d16-d17}` 作为一个整体是 **128 位 = 16 字节**。

### 4.3 `:64` 是什么？—— 对齐说明符（Alignment Specifier），不是数据宽度！

```asm
vst1.8 {d16-d17}, [r0]       ; 无对齐要求：1 字节对齐即可（ARMv7 允许未对齐）
vst1.8 {d16-d17}, [r0 :64]   ; 有对齐要求：r0 必须是 64bit=8 字节的整数倍！
```

- `:64` 的意思是"**我向 CPU 保证地址按 8 字节对齐**"，CPU 可省去未对齐处理 → 更快；
- 假设被打破 → 对齐异常 → SIGBUS。
- 引申：`[r0 :128]` 要求 16 字节对齐，依此类推。

### 4.4 为什么崩（本案例完整链条）

```
静态 buffer 只保证 4 字节对齐（char 数组，实际只保证 1）
    → GCC -O2 生成 16 字节清零时带 :64（要求 8 字节对齐，隐式假设对象≥8 对齐）
    → 链接器把 buffer 放在 0xbc88c4（%8=4，只有 4 对齐）
    → vst1.8 执行时 r0 违反 8 字节对齐 → 对齐异常 → SIGBUS
```

验证：`0xbc88c4 % 8 = 4`（不满足 :64）；`0xbc88c4 % 4 = 0`（换成普通 str 就能跑）。
**同一条程序、同一个地址，指令不同结果不同**——这就是对齐规则的狡猾之处。

## 5. 内存模型与对齐

### 5.1 MMU 页表与虚拟地址（ARMv7 两级页表，完整版）

#### 为什么需要映射

CPU 的 `ldr/str` 用的是虚拟地址（VA，软件看到），内存芯片只认物理地址（PA，RAM 行列）。
32 位 ARM 虚拟空间 4GB，X105 物理内存仅 128MB——靠页表把"用到的虚拟页"映射到"物理页帧"。
动机：隔离（进程互不干扰）、保护（页表项有读写执行/用户内核权限）、按需分配（用到才给物理页）。

#### ARMv7 两级页表（正确数字）

| 项目 | 数值 | 说明 |
|---|---|---|
| 页大小 | 4KB（小页） | 页表管理的最小单位 |
| L1 表 | 4096 项 × 4B = **16KB** | 每项覆盖 **1MB**（4GB/4096），每进程 1 份 |
| L2 表 | 256 项 × 4B = **1KB** | 每项覆盖 4KB（1 页），**用到的 1MB 区才建** |
| 地址拆分 | 12 位 \| 8 位 \| 12 位 | L1 索引(bit31-20) \| L2 索引(bit19-12) \| 页内偏移(bit11-0) |
| TLB | 快表缓存映射 | 避免每次访问都查页表；改映射须 flush（多核需 IPI 通知各核） |
| 段（section）映射 | 1MB 大页 | L1 项直接指向物理帧，不建 L2（内核镜像/只读段常用） |

#### 地址转换走查（以 0xbc88c4 为例）

```
0xbc88c4 = 0x00BC88C4 二进制：
0000 0000 1011 1100 1000 1000 1100 0100
└─ bit31-20: L1 索引 = 0000 0000 1011 = 0x00B = 11
              └─ bit19-12: L2 索引 = 1100 1000 = 0xC8 = 200
                          └─ bit11-0: 偏移 = 1000 1100 0100 = 0x8C4 = 2244
① L1[11]   → 找到 L2 表（1MB 区 0x00B00000~0x00BFFFFF）
② L2[200]  → 找到物理页帧号（如 300）→ 物理基址 = 300 × 4KB
③ 物理地址 = 物理基址 + 0x8C4（页内偏移不走转换）
```

> ⚠️ 拆位要从 bit0 开始数着切：先取低 12 位做偏移，再取 8 位做 L2，剩余（bit31-20）才是 L1。
> 十六进制 1 位 = 4 bit，`0xBC88C4` 只有一个字节是 2 位十六进制，
> 不要按十六进制字节窗口去切（0xBC/0x88/0xC4 是 8|8|8 位，不是 12|8|12 位）。

#### 关键开关：L1 描述符的 bit[1:0]

查页表的第一步永远是固定的——用 VA[31:20] 索引 L1 表取出描述符，**然后看它的 bit[1:0] 决定走哪条路**：

| L1 描述符 bit[1:0] | 含义 | 后续动作 |
|---|---|---|
| `0b00` | 无效（未映射） | 缺页 → 内核介入 |
| `0b01` | 指向 L2 表（粗页表） | 两级走查 → 4KB 小页 |
| `0b10` | **段映射**（1MB 大页） | 一步到位，无 L2 表 |
| `0b11` | 细页表（fine） | ARMv7 已弃用 |

所以"按 12 位还是 20 位拆"不是查之前就定好的——**两种情形都先走 L1，再按读出的类型位现场分派**。
类比：先按门牌号（L1）找到这栋楼，再看门上的牌子——"整层是你的"（段）直接进；"请到 3 楼 205 室"（L2）就再走一趟。

#### L1 描述符的两种格式（32 位）

**段描述符（bit[1:0]=`0b10`）**——管 1MB：

```
位31~20  段物理基址（12 位）   ← 1MB 对齐=低 20 位恒 0，只需存高 12 位（"为什么 12 位"的答案）
位19~12  保留
位11~6   AP 访问权限（读/写/执行、用户/内核）
位2      C（cacheable）  位1~0 = 0b10
```

**L2 表指针描述符（bit[1:0]=`0b01`）**——通往 1MB 的"入口"：

```
位31~10  L2 表物理基址（22 位）  ← 1KB 对齐=低 10 位恒 0，只需存高 22 位
位9~3    保留
位2      C
位1~0    = 0b01
```

#### 段映射 vs 两级映射

| | 段映射（1MB 大页） | 两级页映射（4KB 小页） |
|---|---|---|
| 查表次数 | 1 次（吃 L1 就出结果） | 2 次（L1 → L2） |
| 所需表项 | 1 个 L1 项 | 1 个 L1 项 + 1 张 L2 表（1KB） |
| 映射粒度 | 1MB（可能浪费内存） | 4KB（精细、按需分配） |
| 典型用途 | **内核镜像、只读/代码段**（整段固定连续） | **堆、栈、mmap**（稀疏、动态） |

内核把 vmlinux 镜像挂成段映射：一次命中、省几百个 L2 表项；用户态堆栈按 4KB 一页按需分配，才不浪费 128MB 物理内存。

#### L2 小页描述符（4 字节，简化）

```
位31~12  物理帧号（转换的"答案"）
位8~6    AP[2:0] 访问权限（读/写/执行、用户/内核）
位2      C（cacheable）  位1  B（bufferable）   ← cache 策略（DMA 一致性的根源）
位0      存在位 P：0=未映射(缺页)；1=映射有效
```

#### 缺页与信号判断（查页表之后）

| 现象 | 页表状态 | 内核动作 |
|---|---|---|
| 正常 | P=1 且物理页已分配 | 直接访问 |
| 合法缺页 | P=0 但在进程 VMA 有登记 | 分配物理页→填表项→**重试指令**（用户无感） |
| SIGSEGV | P=0 且 VMA 无登记 / 权限不足 | 非法缺页，发 SIGSEGV |
| SIGBUS | P=1 但访问方式违规（未对齐等） | 对齐异常，发 SIGBUS |

> 案例验证：0xbc88c4 落在 duer_lark 的 RW(.bss) 段（`readelf -l`：0xb8c6d0~0xc8bbb8）→ P=1 映射合法
> → 所以是 **SIGBUS（访问方式违规）而非 SIGSEGV（未映射）**——信号判断先看段布局，再谈对齐。

#### 一次虚拟内存访问的完整流程（总览）

```
应用程序 ldr/str 访问虚拟地址 VA（如 0xbc88c4）
  │
  ▼
① TLB 命中？ ───是──→ 直接得物理地址（无需查页表，最快路径）
  │ 否
  ▼
② 查 L1 表：L1[VA[31:20]]
  │  ├─ 描述符 bit[1:0]=0b10（段） → PA = (段基址<<20) | VA[19:0]      【第 1 次访存】
  │  ├─ 描述符 bit[1:0]=0b01（表） → ③ 查 L2 表：L2[VA[19:12]]
  │  │                                        → PA = (帧号<<12) | VA[11:0]  【第 2 次访存】
  │  └─ 描述符 bit[1:0]=0b00（无效）
  ▼
④ 缺页异常（Data Abort）→ 内核 do_page_fault
  │  ├─ 地址在进程 VMA 登记：分配物理页 → 填页表 → 重试指令（用户无感）
  │  ├─ VMA 无登记 / 权限不足 → SIGSEGV
  │  └─ 映射合法但访问违规（未对齐等）→ SIGBUS
  ▼
⑤ 物理地址交给内存芯片，完成 ldr/str
```

> 正常访问（TLB 命中）只走①；冷启动首次访问走②③；缺页才进④。
> 所以 TLB 命中率是性能命脉 —— 这也是"没改映射就不 flush、多核 flush 要 IPI 通知各核"的原因。

### 5.2 对齐规则（ARMv7）

| 访问方式 | 未对齐（如地址 %8=4 却要求 8 对齐） | 结果 |
|---|---|---|
| 普通 `ldr/str`（字） | ✅ ARMv6 起默认允许 | 正常 |
| `ldm/stm`（多字） | ✅ 但只要求 4 字节对齐 | 正常 |
| **NEON 普通访问** | ❌ 必须自然对齐 | 不可预测/异常 |
| **NEON 带对齐说明符**（`[r0 :64]`） | ❌ 必须 8 字节对齐 | **SIGBUS** |

### 5.3 多核与内存一致性（X105 双核）

- 两核各有 L1 cache，写内存走一致性协议（MESI 类）；
- 需要内存屏障 `dmb/dsb/isb` 保证顺序（spinlock/自旋锁/`MB()` 都在干这事）；
- 意义：读者/写者竞态（如 video_common.c），除了加锁还要考虑**可见性**——
  `volatile` 不管用，需要原子操作或屏障。这是"加了锁还偶发"的隐藏原因。

## 6. 指令集与条件执行

### 6.1 三种指令集

| 模式 | 指令宽度 | 用途 |
|---|---|---|
| ARM | 固定 4 字节 | 高性能，代码密度差 |
| Thumb | 2 字节 | 老 Thumb，密度高 |
| **Thumb-2** | 2/4 字节混合 | 兼顾——**duer_lark 就是它**（cpsr T=1） |

### 6.2 条件执行（ARM 特色）

几乎所有指令可带条件码，无需跳转实现 if/else：

```asm
cmp r0, #0
addne r1, r1, #1   ; Z=0（r0≠0）才执行
addeq r1, r2, #2   ; Z=1（r0=0）才执行
```

条件后缀：`EQ NE CS HS CC LO MI PL VS VC HI LS GE LT GT LE AL`。
**实践**：反汇编看到 `bne/bl/beq` = if；`movne/addne` = 无分支条件执行。

### 6.3 函数调用约定（AAPCS）与栈帧

```asm
; 典型函数前奏/尾声（Thumb-2, -O2）
5f97c: push    {r4, lr}          ; 保存被调用者保存的 r4 + 返回地址
5f980: vmov    q8, #0            ; 16 字节局部变量清零
5f998: vst1.8  {d16-d17}, [r0]   ; 写内存 —— 崩在这
5f99c: ldr     r3, [r2, r3]      ; 栈保护检查（__stack_chk_fail 相关）
5f9a0: pop     {r4, pc}          ; 恢复 r4，lr 弹回 pc 直接返回
```

- `r0-r3` 传参，>4 个走栈；r0 兼返回值；
- **看 push {.., lr} 就是函数入口，pop {.., pc} 就是出口**；
- 结合 sp 是否在栈段内可验证栈帧完整性。

## 8. 中断控制器（GIC）与多核协作

### 8.1 为什么需要 GIC

第 3 节讲了 IRQ 异常（向量表 0x18），但"IRQ 信号是谁拉起来的"没展开。
单核时代设备直接连 CPU 中断引脚；多核时代（X105 双核）需要统一裁决"该给哪个核、谁优先、屏蔽谁"——
这就是 **GIC（Generic Interrupt Controller，ARM 标准中断控制器，X105 为 GICv2）**：

```
单核：VENC/网卡/定时器 ──→ CPU 的 IRQ 引脚（全堆一起，无优先级、无路由）
多核：设备 ──→ GICD（分发器：使能/优先级/路由）──→ 目标核的 GICC（CPU 接口）──→ 该核 IRQ
```

### 8.2 两大部件

| 部件 | 每系统几份 | 职责 |
|---|---|---|
| GICD（Distributor，分发器） | 1 份 | 收拢所有中断源：使能/屏蔽、优先级判优、**路由到哪个核**、pending 管理 |
| GICC（CPU Interface） | **每核 1 份** | 各核读中断号（IAR）、写结束（EOIR） |

### 8.3 中断号三种类型（理解多核的关键）

| 类型 | 全称 | 编号 | 特征 | 例子 |
|---|---|---|---|---|
| SGI | Software Generated | 0~15 | 软件触发，核间通信 | **IPI** |
| PPI | Private Peripheral | 16~31 | 每核私有 | 每核定时器/watchdog |
| SPI | Shared Peripheral | 32+ | 共享外设，可路由任意核 | VENC、以太网、UART |

- **IPI = 用 SGI 实现**：`smp_send_reschedule`（重新调度）、`smp_call_function`（清 TLB、刷 cache）、
  停止其他核（`IPI_CPU_STOP`）——第 5.1 节"多核 flush TLB 要 IPI"即此机制。
- **回连 kernel panic 现场**："CPU0 被 IPI stop 的 idle 栈" = 核心挂了以后用 IPI 命令各核停止；
  停在 idle 的核只是被拉停，真正错误的核在另一份打印（该次缺 CPU1，故分析缺一块）。

### 8.4 中断处理链路（VENC 完成为例）

```
VENC 完成 → GICD 判优路由 → 目标核 GICC → 拉 IRQ → 异常（硬件切 IRQ 模式）
→ 内核读 GICC_IAR 拿中断号 → irq_desc[] 找 handler → 执行 ISR
→ 写 GICC_EOIR → 返回（检查嵌套/抢占）
```

- **上半部/下半部**：ISR（上半部）必须快速、不能睡眠/死等；耗时操作放软中断/workqueue。
  → `video_common.c` 的 reader 应被"中断唤醒"，不能在中断里等锁（会死锁/看门狗）。
- **中断上下文 vs 进程上下文**：中断用 `sp_irq`（影子寄存器），与线程栈隔离，
  → dmp 里看不到"正在执行的中断"，异步插入必须从日志+时间戳推断。

## 10. Cache 与 DMA 一致性

### 10.1 问题：两个"读者"看到不同的世界

CPU 访问内存先经 **Cache**；DMA 设备（VENC/ISP/网卡）**直接读写物理内存**，中间没有 Cache：

```
场景 A：CPU 写，DMA 读            场景 B：DMA 写，CPU 读
  CPU 写 buffer（数据在 Cache）      DMA 写 buffer（直接进内存）
    → 写回策略，未落内存！             → CPU 命中旧 Cache 行
  VENC DMA 读 → 读到旧数据 ❌        CPU 读 → 读到旧数据 ❌
```

### 10.2 Cache 基本结构

- L1（32KB I + 32KB D，每行 32/64B）+ L2；`ldr/str` 先查 L1 → L2 → RAM。
- 写策略：**写回（write-back，脏行延后落盘，嵌入式默认）** vs 写穿（write-through，慢，少见）。
- **Cache Line** = 最小缓存单位（32B/64B），行内地址有低位定位（index）、高位比对（tag）。

### 10.3 一致性操作：两个方向，两样操作

| 方向 | 步骤 | API |
|---|---|---|
| CPU → DMA（先写后读） | CPU 写（脏行）→ **clean 回写** → DMA 读 ✓ | `dma_map_single(...,DMA_TO_DEVICE)` |
| DMA → CPU（先写后读） | DMA 写（进内存）→ **invalidate 丢弃旧行** → CPU 读 ✓ | `dma_map_single(...,DMA_FROM_DEVICE)` / 结束后 `dma_unmap_single` |

- `dma_alloc_coherent()`：一致性内存（non-cacheable 或自动维护），代价是慢，换来"不用手动 sync"。
- **invalidate 会连脏数据一起丢**（清 V 位，无视 D 位）→ 脏行必须先 clean 再 invalidate，否则 CPU 刚写的数据丢失！

### 10.4 页表 C/B 位：Cache 策略的总开关

| 页表位 | 含义 | 典型场景 |
|---|---|---|
| C=1, B=1 | Cacheable + Bufferable | 普通内存（堆/栈/代码） |
| C=0, B=0 | Device / non-cacheable | **外设寄存器**（ioremap）、DMA 描述符、一致性 buffer |

设备寄存器必须 C=0：读带副作用的寄存器（清中断标志）不能被缓存，否则"外设不响应"（读到旧状态死等）。

### 10.5 一致性 vs 顺序性（别混淆）

| 问题 | 管什么 | 手段 |
|---|---|---|
| 一致性 | **值**对不对 | `clean` / `invalidate`（10.3） |
| 顺序性 | **先后**对不对 | 屏障 `dmb`（先于后可见）/ `dsb`（等写完）/ `isb`（刷流水线） |

```c
desc->addr = phys_buf;
desc->len  = size;
dmb();                    // 描述符先就位，再启动 DMA（顺序保证）
writel(ENABLE, DMACTRL);  // 设备此时读描述符一定是最新的
```

### 10.6 排错方法论："数据不对"三连问

1. **谁在写？**（CPU 还是 DMA）→ 确定方向；
2. **走没走 Cache？**（C/B 位、是否一致性内存）→ 确定要不要 sync；
3. **顺序有没有保证？**（写方先、读者后，是否加屏障）→ 确定要不要 barrier。

X105 映射：VENC 取帧花屏→漏 invalidate；送帧出垃圾→漏 clean；死等寄存器→未配 non-cacheable 或少 dsb。

### 10.7 常见疑问（Cache 内部机制详解）

**Q1：CPU 写 buffer 如何确认写进了 Cache 脏行？**

A：**不需要确认——C=1 区域内硬件强制写先进 Cache**，这是写路径的固定行为（write-back + **write-allocate**）：

```
写命中（行已在 Cache）               写缺失（行不在 Cache）★
  CPU 写 buf[i]=x                      CPU 写 buf[i]=x
    → 直接改 Cache 行内容                 → 硬件先整行从内存 fill 进 Cache
    → 自动置 D=1                         → 再改内容，置 D=1
    → 不碰内存 ✓                        → 不碰内存 ✓（只写 4B 却搬整行——粒度是"行"）
```

软件能控制的只有两件事：① 该区域走不走 Cache（页表 C/B 位，C=0 完全绕过）；② 时机（DMA 前 clean）。正确的问题不是"怎么确认写进 Cache"（硬件保证），而是"**DMA 开工前怎么确认脏行已回写**"→ `clean`。

**Q2：Cache 怎么判断哪些行是脏的？**

A：每个 Cache Line 不只存数据，还有一行**元数据**：

```
一个 Cache Line（64B 为例）:
┌──────────────────────────┬────────┬────┬────┬──────────────────┐
│         数据区            │  Tag   │ V  │ D  │                  │
│      64 字节 内容          │ 地址高位 │有效│脏 │                  │
└──────────────────────────┴────────┴────┴────┴──────────────────┘
    （地址低位 index 定位哪一行；tag 比对确认是不是这一行）
```

| 位 | 全称 | 何时置位 | 何时清位 |
|---|---|---|---|
| V | Valid | 行从内存填进来时 | **invalidate 时**（清 V = 丢弃） |
| D | Dirty | **只有写命中时**（读不置） | clean 回写后 / 替换丢弃时 |
| Tag | 标签 | 填表时记录地址高位 | 同 V |

判断流程（硬件全自动）：地址低位定位行（index）→ 比较高位与 Tag → 相等且 V=1 为命中 → 写则改内容并**自动置 D=1**。**脏的本质 = "这一行和内存不一致"**（write-back 下只改了 Cache 没改内存）。替换腾行时看 D：D=1 先回写，D=0 直接丢。读操作永不产生脏行。

**Q3：丢弃（invalidate）和回写（clean）怎么实现？**

A：由 **CP15 协处理器维护指令**执行（特权指令，驱动里调内核 API，机制要懂）：

| 操作 | 汇编本质 | 行为 | 注意 |
|---|---|---|---|
| clean | `mcr p15,0,r0,c7,c10,1` | 行内容写回内存，清 D，**行保留**（V 不变） | 脏行保命用 |
| invalidate | `mcr p15,0,r0,c7,c6,1` | **清 V 位，无视 D 位**，整行作废 | ⚠️ 脏数据直接丢！下次访问 miss 重取内存 |

错误顺序：`invalidate`（脏数据丢！内存是旧的）→ 正确顺序：**先 clean 再 invalidate**。内核实现：`arch/arm/mm/cache-v7.S` 的 `v7_dma_clean_range`/`v7_dma_inv_range` **按行（64B）循环**执行 MCR：
```
v7_dma_inv_range(start, end):
  while (start < end): mcr p15,0,start,c7,c6,1 ; start += 64
```
⚠️ **维护以行为单位 → DMA buffer 必须行首尾对齐**（`dma_alloc_coherent` 保证；手写 buffer 也要对齐），否则首尾行只维护一半 → 混合旧脏数据 → 花屏（"帧边界脏"的微观机制）。

**行的生命周期总览**：

```
             读/写命中(miss→fill)
   ┌───────────────────────────────────────┐
   ▼                                       │
[V=1 D=0] ──写命中，硬件置位──→ [V=1 D=1] ──clean 回写──→ [V=1 D=0]
    │                             │      ▲
    │ 替换时（要腾行）：            │      │行被替换
    │  D=0 → 直接丢掉             │      │ D=0 → 直接丢
    │  D=1 → 先回写再丢            │      │ D=1 → 先回写再丢
    ▼                             ▼      │
                             内存（唯一真身）──────────┘
     invalidate = 直接把 V 清 0（无视 D！）→ 行作废 → 下次从内存重取
```

### 10.8 思维连贯：一条 str 指令的完整三个层（MMU + Cache/DMA 合体）

**修正两个易错点**：
- ❌ "str 触发回写到内存" → ✅ **str 写完停在 Cache 脏行就结束**，物理内存还是旧值。回写只由硬件（行被替换，看 D 位）或软件（显式 `clean`）触发——脏行是**稳定中间态**，write-back 的哲学就是把回写推迟到"不得不"时。
- ❌ "每次写内存都要考虑一致性内存" → ✅ **`dma_alloc_coherent` 只服务于 DMA 交互场景**。判断标准：这个 buffer 会不会被"不经过 Cache 的另一只眼睛"（DMA 设备、其他核）看？会 → 维护/一致性内存；不会 → 正常 str 即可。

**一条 str 指令的全景**：

```
str r0, [r1]      （r1 = 虚拟地址，如 0xBC88C4）
  │
  ▼ ─────────────── 第 1 层：地址转换（永远发生）───────────────
  查页表/TLB → 物理地址 PA
  │  顺带取出页表项的 C/B 位 —— 第 2 层的"入场券"
  ▼ ─────────────── 第 2 层：缓存策略（由 C 位决定）────────────
  ├─ C=1（普通内存）
  │   查 Cache：
  │    ├─ 命中 → 改行内容，硬件置 D=1 ──→ 【结束！内存还是旧值】
  │    └─ 未命中 → 整行 fill 进 Cache → 改行，置 D=1 ──→ 【结束！】
  │   ★ 脏行由别人决定命运：被替换（硬件回写）或你 clean（软件回写）
  └─ C=0（设备寄存器 / 一致性内存）→ 绕开 Cache，直接写物理地址（无脏行概念）
  │
  ▼ ─────────────── 第 3 层：局外人视角（DMA 设备，无 Cache）──────
  这块内存一会儿有 DMA 来读（方向一）→ 必须 clean！否则 DMA 读旧值 ❌
  这块内存刚被 DMA 写完（方向二）  → 必须 invalidate！否则命中旧行 ❌
```

**X105 帧流程（三个层焊死）**：

```
【方向一：CPU 要 VENC 编码一帧】
  ① str 填帧 → 脏行在 Cache（内存旧，无所谓）
  ② 送 VENC 前 dma_map_single(DMA_TO_DEVICE) → clean → 脏行回写
  ③ VENC DMA 读 → 新值 ✓

【方向二：VENC 编码完，CPU 取帧】
  ① VENC DMA 写 → 数据进内存（绕开 Cache）
  ② 中断通知 → 读帧前 dma_unmap_single(DMA_FROM_DEVICE) → invalidate → 旧行作废
  ③ CPU 读 → miss → 从内存取 → 新值 ✓

【dma_alloc_coherent 申请的 buffer】
  ①②③ 合并：C=0 → 双方都直接走内存，不用 clean/invalidate，但每次读写都慢
  （取舍：性能 vs 简单；大帧常交给 dma_buf/mmap 手动维护）
```

**一句话总结**：str 生命周期 = 「VA→PA（转换层）→ 看 C 位（策略层）→ 进脏行（写回层）」；DMA 是链条外的"第二只眼睛"，只看物理内存，所以 **D 位 + C 位就是 CPU 与 DMA 之间唯一的同步信号**。
